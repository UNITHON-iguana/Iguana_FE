# 집계 규칙

집계 화면(`/projects/:id/summary`)이 무엇을 어떻게 세는지 정리한다.
원본은 현장에서 쓰던 엑셀 파일(`BS.xlsm`)이고, 그 파일의 단계를 그대로 옮겼다.

## 단계

```
사진대지 원장
  → 품목 × 작업일 1차 집계   (일일작업현황)
  → HB 가공                  (양면 시공 계수를 곱한 기성 산출값)
  → 기성 누계                (월별 집계 + 누계)
```

구현은 `src/features/summary/aggregate.ts` 하나에 모여 있다.
`aggregate()`가 1차 집계를 만들고, `groupBy()`가 HB를 만든다.
1차 집계의 열을 작업일로 두면 집계표, `YYYY-MM`으로 자르면 기성누계라
**두 화면이 같은 엔진을 쓴다.**

**원본의 `2차 롤업` 표는 옮기지 않았다.** 엑셀에서 `SUM(C16:C26) + SUM(C35:C45)*2`를
쓰려면 중간 합계가 셀에 실제로 있어야 해서 생긴 발판으로 보인다.
우리는 품목 단위에서 계수를 곱해 HB를 바로 내므로 그 발판이 필요 없다.
현장에서 그 표를 실제로 본다는 게 확인되면 `AggregateItem`에 `rollupGroup`을 되살리고
`groupBy(base, items, i => i.rollupGroup)` 한 줄이면 돌아온다.

## 공종마다 세는 방식이 다르다

이 도메인의 핵심이다. 같은 사진대지 한 줄이라도 공종에 따라 품목이 갈리는 기준과
세는 단위가 다르다.

| 공종                              | 규격 입력            | 품목이 갈리는 기준 | 집계 단위 | 환산                        |
| --------------------------------- | -------------------- | ------------------ | --------- | --------------------------- |
| 배관 (금속관/PVC/스파이럴/세대SP) | 호칭경 `65`          | 구분 + 호칭경      | 개소(EA)  | 수량 그대로                 |
| 사각 덕트                         | 가로\*세로 `600*400` | 구분만             | 연장(M)   | `(가로+세로)*2/1000 × 수량` |
| 마감재 (실란트/슬리브)            | 단일 규격            | 구분 + 규격        | 개소(EA)  | 수량 그대로                 |
| 마감재 (차열재/댐퍼테이프/오픈구) | 가로\*세로           | 구분만             | 연장(M)   | 둘레 × 수량                 |

덕트가 개수가 아니라 **둘레 연장 길이**로 기성을 잡는다는 게 배관과의 결정적 차이다.
`600*400` 덕트 2개는 `(600+400)*2/1000 × 2 = 4.0m`이지 2개가 아니다.

## HB 계수 — 벽체는 양면이다

벽체(Wall)는 벽 앞뒤 양면을 시공하므로 기성 산출 시 2를 곱한다.
입상(Riser)은 층을 한 번 관통하므로 1이다. 슬리브는 벽체인데도 단면 시공이라 1이다.

덕트류는 입상·벽체를 가리지 않고 전부 2다 — 원본 산출식이 그렇게 잡혀 있다.

## 프론트가 공종을 추측하지 않는다

**위 규칙은 전부 품목 마스터(`AggregateItem`)가 들고 온다.** 백엔드가 구분과 함께 내려주고,
프론트는 시킨 대로 환산하고 묶기만 한다.

```ts
interface AggregateItem {
  name: string // '금속관벽체50' — 집계표에 찍히는 이름
  category: string // '금속관벽체'   — 사진대지의 구분과 맞춰볼 값
  spec: string | null // '50' / null    — null이면 그 구분의 모든 규격을 받는다
  unit: 'EA' | 'M' // 세는 단위
  multiplier: number // HB 계수 (벽체 2, 입상 1)
  hbGroup: string // HB 가공에서 묶일 이름
}
```

**구분 이름에서 `벽체`를 찾아 2를 곱하는 식의 코드를 넣지 않는다.** 계수도 소구경 경계도
HB 묶음도 전부 현장·발주처마다 달라지는 업무 규칙이라, 프론트에 상수로 박으면 현장 하나
늘 때마다 배포해야 한다. 새 공종이 생겨도 마스터만 바뀌고 코드는 그대로여야 한다.

목 데이터는 `src/mocks/aggregateItems.ts`에 `BS.xlsm` 집계표 시트의 행 목록을 옮겨뒀다.

## 집계표는 한 달치만 본다

작업일이 곧 열이라 기간을 안 자르면 1년짜리 현장에서 열이 이백 개가 되고,
101행 × 200열이면 브라우저가 버틴다 해도 사람이 못 읽는다.
원본 엑셀도 기성 회차마다 시트를 새로 만들어 한두 달치만 담는다(집계표 열이 17개다).

그래서 집계표 탭에는 **월 선택**을 둔다. 범위 선택이 아니라 월 선택이라 한 달 제한이
구조로 강제된다. 기본값은 **오늘이 든 월**이다.
기성누계는 성격이 반대라 기간을 자르지 않는다.

**기간은 집계 결과를 잘라내는 조건이 아니라 집계에 넣을 사진을 고르는 조건이다.**
나중에 서버가 집계하게 되면 이 자리가 그대로 `?from=&to=`가 된다.

안내는 **고른 달이 아니라 프로젝트 전체**를 본다.
달을 옮겼다고 해서 고쳐야 할 일이 사라지면 안 된다.

## 행 목록은 고정이다

값이 하나도 없는 품목도 행이 남는다. 기성 청구 양식이라 행 목록과 순서가 고정이고,
빈 행은 `-`로 찍힌다. 화면에는 `값 없는 품목도 보기` 스위치를 두어 평소에는 감춘다
(기본 꺼짐 — 훑어보는 화면이라 101행 중 대부분이 `-`면 못 읽는다).
**내보내기는 스위치와 무관하게 전체 행을 내야 한다.**

## 검수 완료된 사진만 센다

미검수 값이 섞인 합계는 만들지 않는다. 사진 한 장이 집계에 들어가는 조건은
`confirmBlocker`(`src/lib/workItems.ts`)가 정하고, 사진대지·집계·내보내기가 같은 함수를 쓴다.

- 확인할 칸이 없는 사진은 **분석이 끝나는 즉시 자동으로 확정된다.** 검수는 AI가
  자신 없어 한 사진에만 하는 일이고, 나머지는 올린 즉시 실적이 된다
- 확인 필요한 칸이 남았거나, 작업일이 비었거나, 분석에 실패해 칸이 통째로 빈 사진은
  확정되지 않는다 — 사진대지에서 검수 완료 체크박스가 잠기고 이유가 뜬다
- 그래서 **작업일이 빈 사진이 집계에서 조용히 빠지는 일은 구조적으로 생기지 않는다.**
  작업일이 없으면 확정 자체가 안 되고, 확정되지 않은 사진은 몇 장인지 화면 위에 뜬다

빠진 장수는 집계·내보내기 화면 위에 알린다. 사진대지로 가는 링크를 함께 단다.

## 셀 수 없는 줄은 알린다

조용히 버리면 합계가 말없이 줄어든다. 두 경우를 화면 위에 띄운다.

- 품목 마스터에 없는 구분 — 사진대지에서 고치거나 마스터에 추가해야 한다
- m로 세는 품목인데 규격이 `가로*세로`가 아닌 줄 — 길이를 지어내지 않는다

작업일이 빈 사진도 마찬가지로 임의의 날짜에 밀어넣지 않는다. 다만 위 확정 규칙 때문에
확정된 사진에는 작업일이 늘 있으므로, 이 안내는 규칙이 어긋났을 때를 위한 방어로 남아 있다.

**품목 미매칭은 검수로 막히지 않는다.** 사진대지는 품목 마스터를 모르기 때문에,
구분을 마스터에 없는 말로 적어도 검수 완료가 된다. 이 안내만 집계 화면에 남는 이유다.

## 아직 안 한 것

- **집계를 프론트가 한다.** 사진대지 데이터와 품목 마스터를 둘 다 서버에서 받아
  브라우저에서 붙인다. 백엔드가 없어 만든 프로토타입이고, 제자리는 서버다 —
  엑셀 내보내기도 같은 집계를 해야 하는데 프론트에 두면 같은 업무 규칙이 두 벌이 된다.
  `aggregate.ts`는 DOM도 fetch도 쓰지 않는 순수 함수라(Node로 직접 돌려 검산했다)
  백엔드가 Node면 그대로 옮겨지고, 아니면 이 파일이 명세 역할을 한다.
  옮기고 나면 응답은 이 모양이면 된다.
  `GET /projects/:id/summary?from=&to= → { columns, rows, totals, unmatched }`
- **기성 회차는 월 단위 자동이다.** 원본은 `10~11월`, `2~3월`처럼 달을 묶은 회차를 쓰고
  회차마다 작업일수가 붙는데, 지금은 `YYYY-MM`으로만 나눈다.
  회차를 사람이 만드는 방식이 필요해지면 회차 모델을 따로 둬야 한다
- **집계 결과 내보내기가 없다.** 지금은 화면에서만 본다
