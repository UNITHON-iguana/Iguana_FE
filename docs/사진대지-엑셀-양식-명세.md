# 사진대지 엑셀 양식 명세

백엔드가 사진대지 XLSX를 만들 때 따르는 격자 명세다.
화면(`src/features/photo-sheet/PhotoSheetGrid.tsx`)이 그리는 양식과 같은 모양이어야 한다 —
사용자가 화면에서 고친 그대로 파일이 나와야 하기 때문이다.

원본은 현장에서 쓰던 엑셀 사진대지다. 이 문서는 그 양식을 코드로 옮긴 결과를 적은 것이지
새로 디자인한 게 아니다. 원본과 다른 부분이 발견되면 원본이 기준이다.

## 이 파일을 왜 백엔드가 만드는가

프론트에서도 ExcelJS로 만들 수는 있지만 세 가지 때문에 서버로 넘긴다.

1. **용량** — 사진 300장 × 4MB면 브라우저가 1.2GB를 내려받아 메모리에 올려야 한다.
   서버는 그 파일을 이미 갖고 있다
2. **CORS** — 프론트에서 `fetch`로 이미지 바이트를 읽으려면 이미지 호스트에 CORS 헤더가 필요하다
3. **번들** — `exceljs`가 프론트 번들의 931KB(gzip 258KB)를 차지한다

## 대상 데이터

**검수 완료(`reviewStatus === 'confirmed'`)된 사진만** 내보낸다.
사진번호(`seq`) 오름차순으로 정렬한다.

분석 실패 사진은 검수 완료가 되어 있으면 포함한다 — 사람이 직접 채운 값이기 때문이다.
검수 완료가 아니면 상태와 무관하게 제외한다.

## 넣지 않는 것

작업 진행용 표시는 결과물에 나가지 않는다. 결과물은 깨끗한 양식이다.

- **확인 필요 표시**(`uncertain`)의 노란 배경과 사유 — 검수 화면에서만 쓴다
- **분석 실패 표시**와 실패 사유
- **검수 상태** 자체
- 파일명, 줄 추가·삭제 버튼 같은 화면 도구

`uncertain` 필드는 검수 완료된 사진에도 남아 있을 수 있다(사용자가 확인 필요한 칸을
그대로 둔 채 검수 완료를 누를 수 있다). **그래도 출력에는 반영하지 않는다.**

## 데이터 구조

```
Photo
  seq          사진번호 (623)
  croppedUrl   AI가 분리한 작업 사진. null이면 originalUrl을 대신 쓴다
  originalUrl  원본 사진
  location     위치 ('리테일 4층') — 사진 단위로 하나
  workItems    WorkItem[]

WorkItem                          양식의 한 줄
  category     구분 ('보온덕트입상')
  entries      WorkEntry[]        작업내용

WorkEntry                         규격·수량 한 쌍
  spec         규격 ('1300*800')
  quantity     수량 (0.5)
```

작업일(`workDate`)은 이 양식에 칸이 없다. 사진 안에 현장 카메라 앱이 찍어 넣은
스탬프로만 남는다.

## 블록 구조

사진 한 장이 한 블록이다. 블록은 **작업 항목 줄들 + 위치 줄 하나**로 이뤄진다.

```
     A        B          C        D            E         F         G      H       I
   ┌──────┬─────────┬────────┬────────────┬──────────┬─────────┬─────┬───────┬─────┐
   │      │         │ 구  분 │보온덕트입상│ 작업내용 │1300*800 │ 0.5 │       │     │
   │      │         ├────────┼────────────┼──────────┼─────────┼─────┼───────┼─────┤
   │ 623  │ [사진]  │ 구  분 │무보온덕트입상│ 작업내용 │1300*800 │ 0.5 │       │     │
   │      │         ├────────┼────────────┼──────────┼─────────┼─────┼───────┼─────┤
   │      │         │ 구  분 │ 차열재마감 │ 작업내용 │1300*800 │ 5.5 │       │     │
   │      │         ├────────┴────────────┴──────────┼─────────┴─────┴───────┴─────┤
   │      │         │           위    치             │        리테일 4층           │
   └──────┴─────────┴────────────────────────────────┴─────────────────────────────┘
```

| 열  | 내용                           | 편집 대상   |
| --- | ------------------------------ | ----------- |
| A   | 사진번호                       | 자동 부여   |
| B   | 사진                           | —           |
| C   | `구  분` 라벨                  | 고정 문자열 |
| D   | 구분값 (`category`)            | O           |
| E   | `작업내용` 라벨                | 고정 문자열 |
| F   | 규격 1 (`entries[0].spec`)     | O           |
| G   | 수량 1 (`entries[0].quantity`) | O           |
| H   | 규격 2 (`entries[1].spec`)     | O           |
| I   | 수량 2 (`entries[1].quantity`) | O           |

C·E의 라벨은 **줄마다 반복된다.** 한 번만 쓰고 병합하지 않는다.
`구  분`과 `위    치`는 글자 사이를 벌려 쓴다(원본 양식이 그렇다).

### 병합

블록의 작업 항목 줄이 N개일 때, 블록은 **N+1행**을 차지한다(마지막이 위치 줄).
시작 행을 `r`이라 하면:

| 대상            | 범위            |
| --------------- | --------------- |
| 사진번호        | `A{r}:A{r+N}`   |
| 사진            | `B{r}:B{r+N}`   |
| `위    치` 라벨 | `C{r+N}:E{r+N}` |
| 위치 값         | `F{r+N}:I{r+N}` |

작업 항목 줄(`r` ~ `r+N-1`)의 C~I는 병합하지 않는다.

## 줄 수 규칙

### 최소 3줄

작업 항목이 3줄보다 적으면 **빈 줄로 채워** 3줄을 맞춘다.
빈 줄에도 `구  분`·`작업내용` 라벨은 들어간다(값 칸만 빈다).

상수: `DEFAULT_WORK_ITEM_ROWS = 3` (`src/lib/constants.ts`)

### 규격·수량은 한 줄에 두 쌍까지

원본 양식이 한 줄에 `규격+수량` 쌍을 두 벌만 갖는다. 구분은 같은데 규격이 다른 경우를
한 줄에 적기 위한 칸이다.

상수: `SHEET_ENTRY_SLOTS = 2`

**쌍이 2개를 넘으면 칸을 옆으로 늘리지 않고, 같은 구분을 단 줄을 하나 더 만들어 아래로 흘린다.**

```
구 분 | 보온덕트벽체 | 작업내용 | 2000*800  0.5 | 1600*500  1
구 분 | 보온덕트벽체 | 작업내용 | 900*400   2   |                ← 3번째 쌍이 여기로
```

프론트 구현은 `src/lib/workItems.ts`의 `splitToFormRows(item, slots)`다.
서버도 같은 규칙을 써야 화면과 파일의 줄 수가 같아진다.

```
splitToFormRows(item, slots):
  쌍의 개수가 slots 이하면 그대로 한 줄
  넘으면 slots개씩 잘라 여러 줄로 나누고, 모든 줄이 같은 구분을 갖는다
```

이 규칙 때문에 **블록의 줄 수 N은 `workItems.length`가 아니다.**
줄을 나눈 뒤, 그러고도 3줄이 안 되면 채운 결과가 N이다.

## 사진

- `croppedUrl`을 쓰고, `null`이면 `originalUrl`을 쓴다
- B열 병합 영역 안에 넣고 셀 경계에 맞춘다
- 비율이 깨지지 않게 맞추되 영역을 넘지 않는다
- 검은 실선 테두리
- 사진 안의 스탬프(공사명·공종·위치·내용·일자)는 이미지에 박혀 있으므로 그대로 따라온다.
  별도로 처리할 것 없다

## 서식

### 색

`src/app/theme.ts`가 원본 양식과 맞춰 정한 값이다.

| 대상                                           | 값        | 상수                |
| ---------------------------------------------- | --------- | ------------------- |
| 라벨 칸(`구  분`, `작업내용`, `위    치`) 배경 | `#f0f2f4` | `HEADER_BG`         |
| 구분값 칸(D열) 배경                            | `#eaf0e2` | `SHEET_CATEGORY_BG` |
| 사진번호 글자                                  | `#c0392b` | `SHEET_SEQ_COLOR`   |
| 격자선                                         | `#d4d8dd` | `GRID_LINE`         |
| 본문 글자                                      | `#1f2328` | —                   |

### 정렬·굵기

| 대상     | 정렬   | 굵기          |
| -------- | ------ | ------------- |
| 사진번호 | 가운데 | 굵게, 큰 글씨 |
| 라벨 칸  | 가운데 | 굵게          |
| 구분값   | 가운데 | 보통          |
| 규격     | 가운데 | 보통          |
| 수량     | 오른쪽 | 보통          |
| 위치 값  | 가운데 | 보통          |

### 크기

화면 기준값(px)이다. 엑셀 열 너비 단위가 다르므로 **비율을 유지해 환산**한다.

| 열           | 화면 폭              |
| ------------ | -------------------- |
| A 사진번호   | 48                   |
| B 사진       | 172 (이미지 168×126) |
| C `구  분`   | 62                   |
| D 구분값     | 148                  |
| E `작업내용` | 74                   |
| F 규격 1     | 96                   |
| G 수량 1     | 62                   |
| H 규격 2     | 96                   |
| I 수량 2     | 62                   |

행 높이는 30px. 사진 높이(126)가 작업 항목 3줄(90) + 위치 줄(30) = 120과 맞도록 잡은 값이다.
줄이 4개 이상인 블록에서는 사진이 그만큼 세로로 늘어난 영역 안에 들어간다.

## 확인이 필요한 것

원본 파일을 다시 봐야 정할 수 있는 항목이다. 정해지면 이 문서를 고친다.

- **시트 상단 제목행** — 원본에 `[내화채움 사진대지] 영종도 인스파이어 복합리조트` 형태의
  제목 상자가 있다. 우리 데이터의 무엇을 어떻게 조합하는지(공사명? 공종+공사명?),
  그리고 그 오른쪽에 있는 또 다른 상자(`총…`으로 잘려 보임)가 무엇인지 확인해야 한다
- **두 번째 규격·수량 쌍(H·I열)이 비었을 때 회색 채움을 넣는지.** 원본 스크린샷에서는
  회색으로 보이는데, 빈 칸이라 회색인 건지 항상 회색인 건지 판단할 수 없었다.
  화면에서는 비었을 때만 옅은 회색으로 두고 있다
- **한 시트에 몇 블록을 넣는지, 시트를 나누는지**
- **인쇄 설정**(용지·여백·반복 행) — 엑셀에서 인쇄할 일이 있는지에 달렸다
- **글꼴** — 화면은 Pretendard를 쓰지만 받는 쪽 PC에 없을 수 있다.
  맑은 고딕 같은 기본 글꼴로 지정하는 편이 안전하다
