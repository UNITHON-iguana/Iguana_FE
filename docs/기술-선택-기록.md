# 기술 선택 기록

이 프로젝트에서 무엇을 왜 골랐는지, 아직 정하지 않은 것은 무엇이고 그때 무엇을 따져야
하는지를 남긴다. 코드만 봐서는 알 수 없는 "왜"가 목적이다.

기능명세는 아직 초안이고 백엔드는 정해지지 않았다. 지금 단계의 목표는 **서비스 흐름과
디자인을 시연할 수 있는 프로토타입**이고, 동시에 **앞으로의 개발이 쉬운 구조**를 잡는 것이다.
그래서 아래 선택 중 상당수는 "지금 결정하지 않아도 되게 만드는" 쪽으로 기울어 있다.

## 1. 기반

|            | 선택             | 왜                                                                 |
| ---------- | ---------------- | ------------------------------------------------------------------ |
| 빌드       | **Vite 8**       | 초기 스캐폴딩 그대로. 개발 서버가 빠르고 설정할 게 거의 없다       |
| 프레임워크 | **React 19**     | antd v6가 React 18 이상을 요구한다. 19에서는 호환 패치가 필요 없다 |
| 언어       | **TypeScript 6** | —                                                                  |

### TypeScript 설정에서 걸린 것 두 가지

- **`baseUrl`을 쓸 수 없다.** TS 6.0에서 deprecated 에러가 난다. 경로 별칭은 `paths`만
  `"@/*": ["./src/*"]`로 두고 `vite.config.ts`의 `resolve.alias`와 짝을 맞춘다.
- **`erasableSyntaxOnly: true`** 라서 생성자 파라미터 프로퍼티(`constructor(private x)`)를
  쓸 수 없다. `src/lib/api.ts`의 `ApiError`가 명시적 필드 할당으로 되어 있는 이유다.

## 2. UI 계층

### Ant Design v6 — 왜 이걸 골랐나

처음에는 shadcn/ui를 추천했다가 기획이 바뀌면서 뒤집었다. 판단 근거가 바뀌었기 때문이다.

| 처음 근거                          | 기획 변경 후                                                               |
| ---------------------------------- | -------------------------------------------------------------------------- |
| 작업자용 모바일 페이지의 번들 크기 | **소멸** — 작업자 페이지 자체가 없어졌다. 데스크톱 사내 툴이다             |
| 원청 양식별 가변 표 렌더링         | **축소** — "기본 엑셀 또는 사진대지" 단일 출력이 됐다                      |
| 사진대지 양식은 순수 CSS가 편하다  | **유효하지만 격리됨** — 사진대지 격자 하나만 antd Table 밖에서 만들면 된다 |

반대로 새 기획이 요구하는 것은 전부 batteries-included의 강점 영역이었다.

- 검수 화면: 편집 가능한 표 + 사진 + 상태 배지
- 다중 사진 업로드: 파일별 진행률·실패·재시도 UI
- 필터: 기간·공종·구역·검수 상태 (한국어 로케일 내장)
- 해커톤 MVP: 디자인에 시간을 쓸 여유가 없다

**MUI는 후보에서 뺐다.** DataGrid의 엑셀 내보내기가 Premium(유료)이라 이 제품의 핵심 기능과
정면으로 부딪힌다.

### antd를 계속 쓰는 이유 — "룩" 때문이 아니다

디자인 방향(엑셀처럼 보이게)이 antd 기본값과 많이 다르다면 antd를 쓸 이유가 있느냐는 질문이
나왔다. 답은 이렇다.

**엑셀 느낌과 antd가 충돌하는 건 표면이다** — 색, 반경, 밀도, 격자. 그건 토큰으로 전부
바꿨고 실제로 바꿔서 확인했다. 즉 룩은 우리가 정의한다.

antd가 실제로 주는 건 **동작·로케일·접근성**이다.

- `DatePicker` 한국어 달력, 범위 선택, 키보드 조작
- `Upload.Dragger` 다중 파일, 드래그, 파일별 상태
- `Table` 정렬·고정 헤더·가로 스크롤·로딩
- `Form` 검증과 에러 표시, `Modal` 포커스 트랩·ESC·스크롤 잠금

이걸 직접 만들면 엑셀 느낌에 한 발짝도 못 가고 시간만 쓴다. shadcn으로 갈아타도 이 목록은
그대로 남는다.

antd와 진짜 안 맞는 건 **셀 단위 키보드 이동, 범위 선택, 복붙, 행·열 고정** 같은 스프레드시트
동작인데, 그게 필요한 건 **사진대지 화면 하나**다. 그래서 그 화면만 다르게 만들었다
(`src/features/photo-sheet/PhotoSheetGrid.tsx`).

### @ant-design/icons

antd와 짝이다. 별도 판단 없음.

### Pretendard (npm 패키지, 가변 폰트 동적 서브셋)

**초기에 폰트 이름만 선언하고 실제로 로드하지 않아서 맑은 고딕으로 떨어지고 있었다.**
한글 UI가 촌스러워 보이는 가장 큰 원인이었다.

CDN 대신 npm 패키지를 쓴다 — 런타임에 외부 의존이 없다. 동적 서브셋(92개 파일)이라 실제로는
필요한 글자 영역만 내려받는다.

## 3. 라우팅 — React Router v7

흐름이 곧 라우팅이다.

```
/projects                       프로젝트 목록·생성
/projects/:projectId/sheet      사진대지 — 업로드·AI 분석·검수  ← 본 화면
                    /summary    집계 (작업일별 물량·누계)
                    /export     내보내기 (엑셀/사진대지)
                    ─────────
                    /plan       계획 데이터 + 계획 대비 현황
```

사이드 내비(`src/layouts/AppLayout.tsx`의 `PROJECT_MENU`)가 이 위계를 그대로 따른다.
계획은 나머지 흐름 없이도 돌아가는 곁가지라 구분선 아래에 둔다.

**처음에는 업로드·검수·비교를 각각 한 페이지씩 두었다가 합쳤다.** 업로드와 검수는
같은 사진을 연달아 다루는데 화면을 옮겨야 했고, 계획과 계획 대비 현황은 같은 데이터를
넣고 꺼내 보는 관계였다. 합치기 전 경로(`/upload`, `/review`, `/compare`)는
저장해둔 링크가 깨지지 않게 리다이렉트로 남겨두었다.

**TanStack Router는 타입 안전한 라우팅이 강점이지만 러닝커브를 감수할 만큼의 이득이
지금 없다.** 라우트가 6개뿐이고 동적 세그먼트도 `:projectId` 하나다.

## 4. 데이터 계층 — 이 프로젝트에서 가장 중요한 구조 결정

### 규칙: 화면은 `fetch`나 `axios`를 직접 부르지 않는다

```
src/api/      도메인 함수 — 화면은 여기만 호출한다
src/mocks/    지금은 여기서 인메모리 데이터를 돌려준다
```

```ts
// src/api/photos.ts
export function getPhotos(projectId: string): Promise<Photo[]> {
  return delay(photos.filter(...))   // ← 나중에 http.get(...) 한 줄로 교체
}
```

**이 한 겹 덕분에 지금 fetch냐 axios냐를 결정하지 않아도 된다.** 백엔드 스펙이 나온 뒤
`src/api` 안쪽만 바꾸면 화면 코드는 한 줄도 건드리지 않는다.

기능명세가 초안이라 미확정 항목이 많은 상황에서, **결정을 미룰 수 있게 만드는 것** 자체가
설계 목표였다.

### TanStack Query v5

목 데이터를 돌려주더라도 지금부터 `useQuery`로 감싼다. 로딩·에러 상태가 화면에 자연스럽게
들어가고, 나중에 교체 지점이 `queryFn` 한 줄이다.

**폴링에도 쓴다.** 분석 진행 상태를 이렇게 갱신한다.

```ts
// src/pages/SheetPage.tsx
refetchInterval: (query) =>
  query.state.data?.some((p) => p.status === 'uploading' || p.status === 'analyzing')
    ? 1000
    : false,
```

처리 중인 사진이 남아 있을 때만 다시 묻는다. 백엔드가 충분히 빨라 한 번에 결과가 오면
**이 줄만 지우면 된다.** 실시간 방식이 확정되지 않은 상태에서 양쪽 다 감당하기 위한 선택이다.

쿼리 키는 `src/api/queryKeys.ts`에 모아 둔다.

### 목이 상태를 진행시킨다

`startAnalysis`는 타이머로 사진 상태를 `분석 중 → 완료`로 넘긴다. 백엔드 없이도 데모에서
진행률이 실제로 차오르고, 개별 사진 실패가 다른 사진을 막지 않는다는 규칙도 화면에서 드러난다.

### 색상 리터럴 금지 규칙 — 문서보다 코드가 강하다

```js
// eslint.config.js
'no-restricted-syntax': ['error', {
  selector: "JSXAttribute[name.name='style'] Literal[value=/#[0-9a-fA-F]{3,8}/]",
  message: '색상 리터럴 대신 theme.useToken() 이나 @/app/theme 의 상수를 쓰세요',
}]
```

`CLAUDE.md`에 "색을 직접 박지 마라"고 적어뒀는데도 지켜지지 않았던 적이 있다. 규칙을 글로만
적으면 안 지켜진다. 실효성 순서는 **공통 컴포넌트 > 린트 규칙 > CLAUDE.md > 매번 지시**다.

같은 이유로 `src/components/DataTable.tsx`가 존재한다. 표의 `bordered`/`size`를 화면마다
손으로 반복하면 언젠가 하나가 빠지고 거기만 antd 기본 표가 된다.

## 8. MCP와 도구 — 실제로 무엇이 쓰였나

|                              | 상태                                                 | 이 프로젝트에서 한 역할                   |
| ---------------------------- | ---------------------------------------------------- | ----------------------------------------- |
| **Ant Design MCP**           | `.mcp.json`에 등록, `settings.local.json`에서 활성화 | **아직 실제로 호출된 적 없다**            |
| **frontend-design 플러그인** | `settings.local.json`에서 활성화                     | **아직 실제로 호출된 적 없다**            |
| Figma MCP                    | 세션에 연결됨                                        | 사용하지 않음                             |
| Claude in Chrome             | 세션에 연결됨                                        | 만든 화면이 실제로 렌더링·동작하는지 검증 |

### 기록해둘 것

지금까지의 디자인 작업(토큰 정의, 엑셀풍 전환)은 **antd MCP나 frontend-design 스킬을 거치지
않고** 이뤄졌다. antd 토큰 키 이름과 `prepareComponentToken` 파생 구조는 `node_modules/antd`
소스를 직접 읽어서 확인했다.

**antd MCP의 쓸모는 앞으로다.** `antd_token`으로 실제 존재하는 토큰 키를 확인하면 이름을
지어내는 실수를 막을 수 있다. 다만 한계가 있다 — **MCP는 antd 기본값을 알려줄 뿐 우리가 정한
방향은 모른다.** 그래서 MCP만 믿으면 계속 antd 기본 스타일로 되돌아간다. 그 방어선이
`theme.ts`와 `CLAUDE.md`다.

Claude in Chrome은 검증에 실제로 값을 했다. 이렇게 잡았다.

- antd v6에서 `Alert`의 `message`, `List` 컴포넌트가 deprecated인 것
- 재분석 시 이전 실패 사유가 지워지지 않던 것
- **`td` 패딩이 CSS 명시도에 밀려 적용되지 않던 것** — DOM을 직접 재보고서야 알았다
- CSS 변수(`--ant-color-border`)가 CSS 모듈에서 실제로 해석되는지
- antd의 `fill` 계열 토큰이 반투명이라 양식 라벨 칸이 흐려진다는 것

## 9. 디자인 시스템 흐름

### 방향: 엑셀처럼 보이게 한다

사용자가 하루 종일 엑셀을 쓰는 사무·공무 담당자이고, 결과물 자체가 엑셀 사진대지다.
화면과 출력물이 같은 인상을 줘야 한다.

절충안으로 **회색 격자가 주인공이고 녹색(`#217346`)은 주요 액션에만** 쓴다. 엑셀 녹색을 전면에
쓰면 짝퉁처럼 보이고, 색을 아예 안 쓰면 어디를 눌러야 할지 모른다.

### 네 겹으로 굴러간다

```
   1. src/app/theme.ts          색·간격·타이포의 단일 출처
          │
          ├─ ConfigProvider ──▶ antd 전 컴포넌트 (seed → map → alias 파생)
          │                     · 안 쓴 컴포넌트도 자동으로 따라온다
          │
          ├─ export 상수 ─────▶ antd 토큰에 대응이 없는 개념
          │                     (SHEET_CATEGORY_BG, SHEET_SEQ_COLOR …)
          │
          └─ cssVar ──────────▶ var(--ant-*) → CSS 모듈
                                (PhotoSheetGrid.module.css)

   2. src/components/DataTable  표의 격자·밀도 기본값을 한곳에
   3. eslint no-restricted-syntax  색상 리터럴 차단
   4. CLAUDE.md                 방향을 문서로 남겨 다음 세션에 이어지게
```

**각 겹의 역할이 다르다.**

- **`theme.ts`** — 실체. 여기가 없으면 다른 셋이 가리킬 대상이 없다.
  실제로 `CLAUDE.md`에 규칙이 먼저 있었는데 `theme.ts`가 없어서 지켜지지 않았다.
- **`DataTable`** — 실수할 여지를 없앤다. 규칙을 지키려고 노력할 필요가 없게 만든다.
- **ESLint 규칙** — 어긴 것을 자동으로 잡는다.
- **`CLAUDE.md`** — 사람과 AI에게 방향을 전달한다. 가장 약한 강제력이라 **파일 경로를 명시**해야
  실효가 있다("`src/app/theme.ts`에서만 정의한다").

### antd 토큰이 어떻게 전파되는가

antd v6는 컴포넌트마다 `prepareComponentToken(token)`으로 자기 고유 토큰을 **전역 토큰에서
파생시킨다.**

```js
// node_modules/antd/es/steps/style/index.js — 한 번도 안 쓴 컴포넌트
export const prepareComponentToken = token => ({
  titleLineHeight: token.controlHeight,
  iconFontSize: token.fontSize,
  ...
})
```

즉 `theme.ts`에 `borderRadius: 2`, `fontSize: 12`, `controlHeight: 28`을 정의한 순간
**아직 한 번도 쓰지 않은 컴포넌트도 이미 그 값으로 나온다.**

`theme.ts`의 `components` 블록은 "안 하면 튄다"가 아니라 **파생 결과가 우리 방향과 어긋나는
것만 손보는 자리**다. 예: `Table.headerBg`는 antd 기본 회색이 우리가 원한 회색이 아니라 덮었다.

### 양식 격자를 토큰에 묶은 방법

사진대지 양식은 열 머리글 없이 라벨이 셀 안에 들어가고 사진 칸이 세로로 병합되는 구조라
antd `Table`에 넣지 않고 순수 `<table>`로 짠다. 그런데 색까지 따로 정하면 다른 화면과
어긋난다. 그래서 `cssVar` 모드로 내보낸 CSS 변수를 쓴다.

```css
.sheet td {
  border: 1px solid var(--ant-color-border, #d4d8dd);
}
```

**단, `fill` 계열 토큰은 쓰지 않는다** — 반투명(`rgba(0,0,0,0.02)`)이라 양식의 라벨 칸이
흐려진다. 그런 칸은 `theme.ts`가 export 한 불투명 상수를 인라인으로 받는다.

### 사진대지 화면만 예외인 이유

`PhotoSheetGrid`는 antd `Table`을 쓰지 않고 `<table>`을 직접 그린다. 사진 한 장이
사진번호·사진 칸을 세로로 병합한 덩어리가 되어야 하는데, 그건 원본 엑셀 양식의 구조지
데이터 표의 구조가 아니다.

**테두리 없는 입력칸을 셀마다 항상 깔아둔다.** 클릭하면 바로 타이핑되고, 셀 안에 또 테두리가
생기지 않는다. Tab 이동은 브라우저 기본 순서를 그대로 쓰고 Enter·방향키만 직접 처리한다.

사진 크기만은 CSS가 아니라 props로 준다 — **antd가 런타임에 넣는 `.ant-image-img` 규칙이
나중에 붙어 같은 명시도의 CSS 모듈 클래스를 이긴다.**

## 10. 아직 정하지 않은 것

### zod — 도입 시점: 계획 데이터 엑셀 파싱을 실제로 구현할 때

**폼 검증용이 아니다.** antd `Form`이 자체 `rules`를 갖고 있어 입력 폼에는 필요 없다.

쓸 곳은 **엑셀 행 검증**이다. 명세가 이렇게 요구한다.

> 유효하지 않은 행은 **행 번호와 오류 사유**를 표시하고 수정 후 다시 등록하게 한다

행마다 `safeParse` 하고 `error.issues`의 `path`(어느 열)와 `message`(사유)를 그대로 표에
뿌리면 된다. 직접 짜면 가장 지저분해지는 코드다. 필수 열 누락 검사도 같은 스키마로 처리된다.

부차적으로 AI/OCR 응답 검증에도 쓸 수 있다(전 필드가 nullable이라 서버가 예상 밖 형태를 줘도
화면이 안 깨지게). 다만 그것만으로는 도입할 이유가 약하다.

### HTTP 클라이언트 — fetch vs axios

지금은 결정하지 않아도 된다. `src/api` 뒤에 숨어 있다.

`src/lib/api.ts`에 fetch 기반 클라이언트가 작성만 되어 있고 아직 아무 데서도 import하지 않는다.

**결정을 부르는 조건은 업로드 진행률이다.** `fetch`는 업로드 진행률을 낼 수 없다 — 라이브러리
취향이 아니라 API의 한계다. 필요해지면 두 갈래다.

1. JSON은 fetch 유지 + 파일 업로드만 XHR (antd `Upload`의 `customRequest`가 `onProgress`를 준다)
2. axios로 통일 (`onUploadProgress` 내장)

의존성을 늘리지 않는 1번이 무난하지만, 팀이 axios에 익숙하면 2번도 합리적이다.

추가로 **현재 `api.ts`는 항상 `res.json()`이라 blob 다운로드를 못 받는다.** 엑셀·사진대지
파일을 서버에서 받아야 한다면 `getBlob`을 더해야 한다.

### 실시간 분석 상태 — 폴링 / SSE / WebSocket

|                 | 특징                                                       |
| --------------- | ---------------------------------------------------------- |
| **폴링** (현재) | 구현 가장 단순, 백엔드도 REST 하나면 끝                    |
| SSE             | 서버→클라 단방향 푸시. 진행률에 잘 맞지만 백엔드 작업 필요 |
| WebSocket       | 양방향. 이 서비스엔 과하다                                 |

**백엔드 처리 시간에 달렸다.** 몇 초 안에 끝나면 요청 한 번으로 충분하고 `refetchInterval`만
지우면 된다. 수십 초 이상 걸리면 SSE를 검토할 만하다.

사진별 상태 자체는 어느 쪽이든 필요하다 — 명세가 "개별 사진 분석 실패는 전체 분석 실패로
처리하지 않는다"고 정하고 있다.

### 인증·권한 — 프로토타입에서 제외

명세 전반에 "사무 담당자와 공무 담당자만"이라는 조건이 반복되지만, 시연 흐름을 짧게 하려고
로그인을 넣지 않았다. 넣게 되면 필요한 것:

- `api.ts`에 Authorization 헤더, 401 처리
- 라우트 가드
- 토큰 저장 위치 결정

### 사진대지 출력 형식 — 엑셀 한 가지

**PDF 출력은 하지 않기로 했다.** 브라우저 인쇄로 PDF를 만들던 경로와 A4 조판
(`PhotoSheet`)을 걷어냈다. 원본 샘플이 엑셀이고 받는 쪽도 엑셀로 고쳐 쓰기 때문에,
결과물을 엑셀 하나로 모으는 편이 화면과 출력물을 일치시키기 쉽다.

남은 일은 **엑셀 출력을 원본 양식 형태로 만드는 것**이다. 지금 `features/export/excel.ts`는
집계용 평면 표(사진번호·작업일·위치·구분·규격·수량)만 만들고 사진을 넣지 않는다.
ExcelJS의 `addImage`로 사진을 박고 셀 병합으로 `구 분`/`작업내용`/`위 치` 양식을
재현해야 화면에서 보던 것과 같은 파일이 나간다.

## 11. 알려진 부채

- **`PhotoSheetGrid`의 `data-row`는 배열 인덱스다.** 이 표에 정렬이나 페이지네이션을 켜면
  방향키가 에러 없이 조용히 어긋난다. 코드에 주석으로 못 박아 뒀다.
- **옛 키 이름(`Down`, `Up`, `Esc`) 대응은 방어 코드다.** 방향키가 동작하지 않던 문제의 원인이
  IME 조합이었는지 키 이름이었는지 끝내 가리지 못했다. 표준 이름만으로 충분하다고 확인되면
  지워도 된다.
- **성능은 손대지 않았다.** 키 하나마다 카드 전체가 리렌더되고 `columns`가 매번 새로 생성된다.
  체감 지연은 대략 50행부터인데 실제 데이터는 3~10행이라 지금 최적화하면 코드만 복잡해진다.
  필요해지면 `columns`를 `useMemo`로 고정한다.
- **자리표시 이미지가 회색 사각형이다.** 사진이 주인공인 서비스라 시연 인상에 손해다.
